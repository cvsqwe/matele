# Вебхуки

При long polling бот сам постоянно спрашивает мессенджер о новых событиях. С вебхуками наоборот: вы сообщаете мессенджеру адрес своего сервера, и он отправляет каждое событие HTTP-запросом на этот адрес.

Вебхуки нужны в двух случаях:

- бот работает рядом с веб-приложением, которое уже принимает HTTP-запросы, и заводить для него отдельный процесс не хочется;
- боту нужно несколько процессов, потому что один перестал справляться.

Для начала и для небольших ботов polling проще: ему не нужен ни домен, ни сертификат. Хендлеры в обоих случаях одни и те же, так что перейти можно в любой момент.

## Запуск

Поставьте `matele[webhook]`. Вместе с ним установится uvicorn, сервер, который будет принимать запросы.

```python
from matele import Dispatcher
from matele.max import MaxBot
from matele.telegram import TelegramBot
from matele.webhook import Webhook

dp = Dispatcher()
# ... хендлеры ...

webhook = Webhook(dp, base_url="https://bot.example.com")
webhook.add(MaxBot(MAX_TOKEN), "/max")
webhook.add(TelegramBot(TG_TOKEN), "/telegram")

if __name__ == "__main__":
    webhook.run(host="127.0.0.1", port=8080)
```

`base_url` это публичный адрес вашего сервера, а `webhook.add()` назначает каждому боту свой путь на нём.

При запуске `Webhook` делает то же, что `run_polling`, и ещё немного:

1. узнаёт у каждого мессенджера, кто он (`get_me`);
2. публикует меню команд;
3. регистрирует в мессенджерах адреса `https://bot.example.com/max` и `https://bot.example.com/telegram`.

При остановке он ждёт до 10 секунд, пока доработают начатые хендлеры, и закрывает ботов и хранилище.

`webhook.run()` принимает `host`, `port` и любые другие параметры uvicorn. По умолчанию сервер слушает все сетевые интерфейсы. Если перед ботом стоит nginx на той же машине, укажите `host="127.0.0.1"`, как в примере, чтобы бот не был доступен снаружи в обход него.

## Требования мессенджеров

Нужен публичный адрес HTTPS с настоящим сертификатом. MAX принимает только порт 443, Telegram порты 443, 80, 88 и 8443.

Сам бот HTTPS не умеет и не должен: он слушает локальный порт по обычному HTTP, а перед ним стоит nginx или Caddy, который принимает HTTPS на 443 и передаёт запросы боту.

```nginx
server {
    listen 443 ssl;
    server_name bot.example.com;
    # ssl_certificate ... (например, от Let's Encrypt)

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

С Caddy то же самое занимает две строки, а сертификат он получит сам:

```text
bot.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

### Проверка на своём компьютере

Для разработки подойдёт туннель вроде cloudflared или ngrok. Он даёт временный HTTPS-адрес, который ведёт на ваш компьютер. Этот адрес передают в `base_url`:

```bash
cloudflared tunnel --url http://127.0.0.1:8080
```

Используйте для таких проверок тестового бота. Регистрация вебхука с боевым токеном переключит на ваш компьютер события настоящего бота.

## Безопасность

Адрес вебхука можно угадать или подсмотреть, и тогда кто угодно сможет присылать боту поддельные события от имени любого человека. Поэтому `Webhook` при регистрации передаёт мессенджерам случайный секрет, а мессенджеры присылают его в заголовке каждого запроса. Запросы без верного секрета получают ответ 403 и не обрабатываются.

По умолчанию секрет генерируется заново при каждом запуске и нигде не хранится. Этого достаточно, пока процесс один.

Если процессов несколько, у каждого окажется свой секрет, и мессенджер будет знать только последний из них. Задайте общий:

```python
import os

webhook = Webhook(dp, base_url="https://bot.example.com", secret=os.environ["WEBHOOK_SECRET"])
```

Секрет должен состоять из 5-256 символов: латинские буквы, цифры, `_` и `-`.

Тела запросов больше 4 МБ отклоняются с ответом 413: настоящие события занимают несколько килобайт.

## Как обрабатываются запросы

`Webhook` сразу отвечает мессенджеру 200, а событие обрабатывает в фоне. Иначе медленный хендлер заставил бы мессенджер решить, что сервер не ответил, и прислать событие ещё раз.

События одного человека, как и при polling, обрабатываются по очереди, события разных людей одновременно.

Коды ответов, которые возвращает `Webhook`:

| Код | Когда |
|---|---|
| 200 | событие принято |
| 403 | неверный или отсутствующий секрет |
| 404 | по этому пути нет бота |
| 405 | запрос не методом POST |
| 400 | тело запроса не JSON |
| 413 | тело запроса больше 4 МБ |
| 503 | бот перегружен, см. ниже |

Если событие пришло с верным секретом, но разобрать его не удалось, оно записывается в лог, а мессенджер всё равно получает 200. Иначе он присылал бы сломанное событие снова и снова.

Telegram иногда присылает одно и то же событие повторно, если не получил ответ вовремя. Такие повторы matele узнаёт по номеру события и не обрабатывает второй раз.

### Перегрузка

Если хендлеры не успевают и в очереди накопилось 1000 событий, новые запросы получают ответ 503, и мессенджер пришлёт их позже. Так всплеск событий не съедает всю память процесса. Порог меняется параметром `max_pending`:

```python
webhook = Webhook(dp, base_url="https://bot.example.com", max_pending=5000)
```

### Чтобы события не терялись

Если процесс упадёт после ответа 200, но до конца работы хендлера, это событие потеряется: мессенджер считает его доставленным. Для ботов, где это недопустимо, есть режим «минимум один раз»:

```python
webhook = Webhook(dp, base_url="https://bot.example.com", at_least_once=True)
```

В нём `Webhook` отвечает мессенджеру только после того, как событие обработано. Не получив ответа, мессенджер пришлёт событие снова после перезапуска.

У режима два условия. Хендлеры должны спокойно переносить повтор события, например проверять, не создан ли заказ, прежде чем создавать его. И они должны работать быстро: мессенджер ждёт ответа ограниченное время. Если он не дождался и повторил запрос, пока хендлер ещё работает, второй раз событие не обрабатывается: повторный запрос получит ответ, когда закончится первый. Если остановка процесса прервала хендлер, мессенджер получит ответ 503 и пришлёт событие снова.

Подробнее о том, когда этот режим нужен, написано в разделе [Чтобы события не терялись](deploy.md#чтобы-события-не-терялись).

## Другие ASGI-серверы и фреймворки

`Webhook` это обычное ASGI-приложение, поэтому его можно запустить любым ASGI-сервером, а не только через `webhook.run()`:

```bash
uvicorn bot:webhook --host 127.0.0.1 --port 8080
```

### Внутри приложения на FastAPI или Starlette

Если у вас уже есть веб-приложение, вебхук можно подключить внутрь него, и бот будет работать в том же процессе:

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI

webhook = Webhook(dp, base_url="https://bot.example.com/hooks")
webhook.add(MaxBot(MAX_TOKEN), "/max")
webhook.add(TelegramBot(TG_TOKEN), "/telegram")


@asynccontextmanager
async def lifespan(app: FastAPI):
    await webhook.startup()
    yield
    await webhook.shutdown()


app = FastAPI(lifespan=lifespan)
app.mount("/hooks", webhook)  # адреса станут /hooks/max и /hooks/telegram
```

Два момента, на которых легко ошибиться. `base_url` должен включать префикс, под которым подключён вебхук: здесь это `/hooks`. И приложение, подключённое через `mount`, не получает от FastAPI событий запуска и остановки, поэтому `webhook.startup()` и `webhook.shutdown()` нужно вызвать самим, как в примере.

Из хендлеров FastAPI можно отправлять сообщения через те же объекты ботов, например уведомить человека о том, что его заказ оплачен.

### В любом другом фреймворке

Обработку можно вызвать вручную. `handle()` принимает путь, заголовки и тело запроса и возвращает HTTP-код, которым нужно ответить:

```python
status = await webhook.handle("/telegram", request.headers, await request.body())
```

`startup()` и `shutdown()` в этом случае тоже вызываются вручную.

### Регистрация адресов вручную

Если не передать `base_url`, `Webhook` не будет регистрировать адреса в мессенджерах. Тогда это делается один раз самостоятельно, например скриптом при выкладке:

```python
await telegram_bot.set_webhook("https://bot.example.com/telegram", secret=SECRET)
await max_bot.set_webhook("https://bot.example.com/max", secret=SECRET)
```

Секрет в этом случае обязательно передайте и в `Webhook(dp, secret=SECRET)`, иначе он сгенерирует свой и будет отклонять все запросы.

## Переход обратно на polling

Пока в мессенджере зарегистрирован вебхук, события через polling не приходят: и Telegram, и MAX отправляют их на адрес вебхука.

matele не удаляет вебхук сам. Он может принадлежать работающему боту, и локальный запуск с тем же токеном оставил бы его без событий. Вместо этого polling пишет в лог предупреждение с адресом вебхука.

Чтобы вернуться на polling, удалите вебхук явно. Есть три способа.

Удалять его при остановке сервера:

```python
webhook = Webhook(dp, base_url="https://bot.example.com", delete_on_shutdown=True)
```

Удалить один раз вручную:

```python
await telegram_bot.delete_webhook()
await max_bot.delete_webhook("https://bot.example.com/max")
```

Разрешить Telegram-боту удалять вебхук при запуске polling:

```python
telegram_bot = TelegramBot(TG_TOKEN, replace_webhook=True)
```

Последний способ удобен при разработке, но не ставьте его в код, который может быть запущен с боевым токеном.

# Состояния

Бот получает сообщения по одному и сам по себе не помнит, о чём шёл разговор. Если он спросил «Как вас зовут?», то следующее сообщение человека это имя, а не случайный текст. Чтобы бот это понимал, нужно где-то запомнить, какой вопрос был задан.

Этим занимается состояние. `ctx.state` хранит, на каком шаге разговора человек сейчас, и данные, которые он уже ввёл. Хендлер можно привязать к шагу, и тогда он получит только сообщения людей, которые на этом шаге находятся.

## Анкета из трёх шагов

```python
from matele import Context, State, StatesGroup, escape


class Signup(StatesGroup):
    name = State()
    age = State()
    city = State()


@dp.command("signup", description="Заполнить анкету")
async def signup(ctx: Context):
    ctx.state.set(Signup.name)
    await ctx.reply("Как вас зовут?")


@dp.command("cancel", description="Отменить")
async def cancel(ctx: Context):
    ctx.state.clear()
    await ctx.reply("Отменено")


@dp.message(state=Signup.name)
async def got_name(ctx: Context):
    ctx.state.update(name=ctx.text)
    ctx.state.set(Signup.age)
    await ctx.reply("Сколько вам лет?")


@dp.message(state=Signup.age)
async def got_age(ctx: Context):
    if not ctx.text.isdigit():
        await ctx.reply("Напишите возраст числом")
        return
    ctx.state.update(age=int(ctx.text))
    ctx.state.set(Signup.city)
    await ctx.reply("Из какого вы города?")


@dp.message(state=Signup.city)
async def got_city(ctx: Context):
    name, age = ctx.state.get("name"), ctx.state.get("age")
    ctx.state.clear()
    await ctx.reply(f"Готово: {escape(name)}, {age}, {escape(ctx.text)}")
```

Разберём, что здесь происходит.

`StatesGroup` это набор шагов одного сценария. Каждый `State()` внутри него это один шаг.

`ctx.state.set(Signup.name)` переводит человека на шаг `name`. Следующее его сообщение попадёт в хендлер с `state=Signup.name`.

`ctx.state.update(name=ctx.text)` запоминает введённое. Данные лежат рядом с состоянием и доступны на следующих шагах через `ctx.state.get()`.

В хендлере возраста есть проверка. Если человек написал не число, хендлер отвечает и выходит, не меняя состояние. Человек остаётся на том же шаге, и следующее сообщение снова придёт сюда.

`ctx.state.clear()` заканчивает разговор: сбрасывает и состояние, и данные.

`/cancel` работает на любом шаге, потому что команды проверяются раньше хендлеров состояний (см. [порядок хендлеров](handlers.md#порядок-хендлеров)). Без этого человек, передумавший заполнять анкету, застрял бы в ней: любое его сообщение считалось бы ответом на вопрос.

## Что умеет ctx.state

| Вызов | Что делает |
|---|---|
| `ctx.state.set(Signup.age)` | перейти в состояние |
| `ctx.state.set(None)` | выйти из состояния, данные останутся |
| `ctx.state.current` | имя текущего состояния или `None` |
| `ctx.state.is_in(Signup)` | человек на одном из шагов анкеты |
| `ctx.state.update(age=30)` | сохранить данные |
| `ctx.state.get("age")` | прочитать данные, `None`, если их нет |
| `ctx.state.get("age", 18)` | прочитать данные со значением по умолчанию |
| `ctx.state.data` | все данные словарём |
| `ctx.state.clear()` | закончить разговор: ни состояния, ни данных |

Всё это обычные синхронные вызовы, без `await`. matele загружает состояние из хранилища перед хендлером и сохраняет после, только если оно изменилось.

Состояние сохраняется и тогда, когда хендлер упал с ошибкой. Поэтому `ctx.state.set()` лучше вызывать в конце хендлера, когда всё, что могло не получиться, уже получилось. Подробнее в разделе [Ошибки](errors.md#когда-падает-хендлер).

## Какие хендлеры к чему привязаны

Параметр `state` есть у `message`, `command`, `callback` и `raw_callback`:

| Параметр | Когда срабатывает хендлер |
|---|---|
| `state=Signup.name` | только на шаге `name` |
| `state=Signup` | на любом шаге анкеты |
| `state=(Signup.age, Signup.city)` | на одном из перечисленных шагов |
| `state=None` | только когда человек не находится ни в каком состоянии |
| не указан | всегда, в любом состоянии и без него |

Обратите внимание на разницу между `state=None` и отсутствием параметра. Хендлер без `state` срабатывает всегда. Хендлер с `state=None` срабатывает только вне сценариев.

Привязка ко всей группе удобна для общих действий внутри сценария:

```python
@dp.command("back", state=Signup)
async def back(ctx: Context):
    await ctx.reply("Вернуться можно только в начало: /signup")


@dp.message(HasAttachment(), state=Signup)
async def no_files(ctx: Context):
    await ctx.reply("В анкете нужен только текст")
```

Хендлер, привязанный к состоянию, проверяется раньше хендлера без привязки, так что общий `@dp.message()` не перехватит ответ на вопрос анкеты.

### Кнопки внутри сценария

К состоянию можно привязывать и нажатия кнопок. Так делают шаги с выбором из вариантов:

```python
@callback("signup:plan")
class ChoosePlan(CallbackData):
    plan: Literal["free", "pro"]


@dp.callback(ChoosePlan, state=Signup.plan)
async def chose_plan(ctx: Context, payload: ChoosePlan):
    ctx.state.update(plan=payload.plan)
    ctx.state.set(Signup.confirm)
    await ctx.edit("Подтвердите заявку", confirm_keyboard)
```

Привязка к состоянию здесь защищает от старых кнопок: если человек нажмёт кнопку выбора тарифа из прошлой, уже законченной анкеты, хендлер не сработает.

## Имена состояний

Состояние хранится по имени. По умолчанию имя составляется из имени класса и атрибута: `"Signup:name"`.

Из этого следует неприятность. Если переименовать класс или атрибут, люди, которые в этот момент были на этом шаге, окажутся в состоянии, которого больше нет. Их сообщения пойдут в общие хендлеры, как будто анкеты не было. Чтобы имя не зависело от кода, задайте его явно:

```python
class Signup(StatesGroup):
    name = State("signup:name")
    age = State("signup:age")
```

Теперь класс и атрибуты можно переименовывать свободно.

Состояние можно объявить и вне группы, тогда имя обязательно:

```python
ASK_EMAIL = State("profile:email")
```

Это удобно для сценариев из одного шага.

## Где хранятся состояния

По умолчанию состояния лежат в памяти процесса и теряются при перезапуске: человек, который заполнял анкету, после перезапуска бота окажется вне её. Для разработки это нормально, для настоящего бота нет. Подключите хранилище:

```python
from matele.fsm import RedisStorage, SQLiteStorage

# один процесс бота
dp = Dispatcher(storage=SQLiteStorage("bot.db"))

# несколько процессов или серверов
dp = Dispatcher(storage=RedisStorage.from_url("redis://localhost:6379/0"))
```

`run_polling` и вебхуки сами закрывают хранилище при остановке бота.

### SQLite

`SQLiteStorage` хранит состояния в файле. Он работает на стандартной библиотеке Python и не требует ни сервера, ни дополнительных пакетов. Запросы выполняются в отдельном потоке и не задерживают остальных людей.

Это правильный выбор для бота, который работает одним процессом, то есть для большинства ботов. В том же файле можно хранить ключи длинных кнопок Telegram, см. [Длина данных](buttons.md#длина-данных).

### Redis

`RedisStorage` нужен, когда бот работает в нескольких процессах или на нескольких серверах и состояние должно быть общим. Для него требуется пакет `matele[redis]`.

Если у разговоров должен быть срок жизни, передайте `ttl` в секундах:

```python
storage = RedisStorage.from_url("redis://localhost:6379/0", ttl=7 * 86400)
```

Разговор, который не менялся неделю, удалится сам. Чтение срок не продлевает, только изменение.

Когда хранилище делят несколько процессов, события одного человека могут попасть в разные процессы одновременно. Чтобы один процесс не затёр состояние, сохранённое другим, `RedisStorage` на время обработки события берёт в Redis блокировку этого разговора, и второй процесс ждёт. Блокировка снимается сама через `lock_ttl` секунд (по умолчанию 60), чтобы упавший процесс не заблокировал человека навсегда. Если ваши хендлеры могут работать дольше минуты, увеличьте `lock_ttl`.

### Что можно хранить

Данные в `ctx.state` сохраняются как JSON, поэтому в них можно класть строки, числа, `bool`, `None`, списки и словари из них. Объекты своих классов, даты и множества напрямую сохранить не получится.

Не храните в состоянии объекты из базы. Храните их id и загружайте объект заново на каждом шаге: так данные не устареют, а состояние останется маленьким.

```python
ctx.state.update(order_id=order.id)          # хорошо
ctx.state.update(order=order)                # не сохранится в SQLite и Redis
```

### Своё хранилище

Хранилище это любой класс с четырьмя async-методами:

```python
from matele.fsm import StateRecord, StorageKey


class MyStorage:
    async def get(self, key: StorageKey) -> StateRecord | None: ...

    async def set(self, key: StorageKey, record: StateRecord) -> None: ...

    async def delete(self, key: StorageKey) -> None: ...

    async def close(self) -> None: ...
```

`key` это `StorageKey(platform, user_id, chat_id)`, где `chat_id` равен `None` для личного чата. `record` это `StateRecord` с полями `state` (имя состояния или `None`), `data` (данные хендлеров) и `meta` (служебные данные matele, например id сообщения-меню).

Если хранилище общее для нескольких процессов, добавьте пятый, необязательный метод `lock(key)`. Он должен возвращать async-контекстный менеджер, который держит блокировку разговора, пока обрабатывается событие.

## Чьё это состояние

Состояние хранится отдельно для каждого человека в каждом мессенджере. Анкета, начатая в Telegram, не продолжится в MAX: для matele это два разных собеседника.

В группе состояние отдельное для человека в этой группе. Анкета, начатая в одной группе, не мешает в другой и в личном чате. А два человека в одной группе заполняют каждый свою анкету и друг другу не мешают.

Одного человека matele обрабатывает последовательно: пока не закончился хендлер его предыдущего сообщения, следующее ждёт. Поэтому хендлер может спокойно читать и менять состояние, не опасаясь, что параллельно его меняет другой хендлер того же человека. Сообщения разных людей обрабатываются одновременно.

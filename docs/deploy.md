# Запуск на сервере

Бот на ноутбуке работает, пока открыт терминал. Чтобы он работал круглосуточно, его нужно перенести на сервер и настроить так, чтобы он переживал перезапуски, сбои сети и собственные ошибки. На этой странице собрано всё, что для этого нужно решить.

Короткая версия для небольшого бота:

1. оставьте long polling, вебхуки вам пока не нужны;
2. подключите `SQLiteStorage`, чтобы состояния переживали перезапуск;
3. храните токены в переменных окружения;
4. запустите бота через systemd или Docker с автоматическим перезапуском;
5. добавьте обработчик ошибок и настройте логи.

Дальше каждый пункт подробно.

## Polling или вебхуки

При long polling бот сам спрашивает мессенджер о новых событиях. Ему не нужны ни домен, ни сертификат, ни открытые порты: достаточно исходящего доступа в интернет. Он работает за NAT, на домашнем сервере и в любом облаке.

При вебхуках мессенджер сам отправляет события на ваш сервер. Для этого нужен публичный адрес с HTTPS.

Начинайте с polling. Переходить на вебхуки стоит в двух случаях: бот живёт рядом с веб-приложением, которое уже принимает запросы, или один процесс перестал справляться и боту нужно несколько. С polling один токен может обслуживать только один процесс.

Про настройку вебхуков есть отдельная страница: [Вебхуки](webhooks.md).

## Хранилище состояний

По умолчанию состояния разговоров лежат в памяти. После каждого перезапуска бот забудет, кто на каком шаге анкеты и где у кого [меню](menus.md).

```python
from matele import Dispatcher
from matele.fsm import SQLiteStorage

dp = Dispatcher(storage=SQLiteStorage("/var/lib/my-bot/state.db"))
```

Положите файл базы туда, где он переживёт обновление кода, то есть не в папку с репозиторием. В Docker это должен быть том.

Если бот работает в нескольких процессах, нужен `RedisStorage`. Подробнее в разделе [Где хранятся состояния](states.md#где-хранятся-состояния).

## Секреты

Токены ботов, секрет вебхука и секрет подписи кнопок нельзя хранить в коде и в репозитории. Передавайте их через переменные окружения:

```python
import os

from matele.max import MaxBot
from matele.telegram import TelegramBot

max_bot = MaxBot(os.environ["MAX_BOT_TOKEN"])
telegram = TelegramBot(os.environ["TELEGRAM_BOT_TOKEN"])
```

На сервере переменные удобно держать в отдельном файле с правами только для пользователя, от которого работает бот:

```bash
# /etc/my-bot/env, chmod 600
MAX_BOT_TOKEN=...
TELEGRAM_BOT_TOKEN=...
```

Если токен всё же попал в репозиторий или в чат, считайте его скомпрометированным и выпустите новый: в Telegram это делает @BotFather командой `/revoke`, в MAX токен перевыпускается в настройках бота.

Для разработки заведите отдельного тестового бота со своим токеном. Запуск локальной копии с боевым токеном забирает события у работающего бота.

## Запуск через systemd

На обычном Linux-сервере проще всего оформить бота как сервис systemd. Он запустит бота при загрузке сервера и перезапустит, если тот упадёт.

```ini
# /etc/systemd/system/my-bot.service
[Unit]
Description=My bot
After=network-online.target
Wants=network-online.target

[Service]
User=bot
WorkingDirectory=/opt/my-bot
EnvironmentFile=/etc/my-bot/env
ExecStart=/opt/my-bot/.venv/bin/python bot.py
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now my-bot
sudo journalctl -u my-bot -f      # смотреть лог
```

## Запуск в Docker

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "bot.py"]
```

В `requirements.txt` перечислены зависимости бота, например `matele==0.2.0`. Точная версия защищает от того, что новая версия matele с ломающими изменениями приедет при очередной сборке образа.

```bash
docker run -d --name my-bot --restart unless-stopped --stop-timeout 20 \
  --env-file /etc/my-bot/env \
  -v my-bot-data:/data \
  my-bot
```

Файл базы состояний положите на том: `SQLiteStorage("/data/state.db")`.

Запускайте бота именно так, как в примере, через `CMD ["python", "bot.py"]` в виде списка. Если написать команду строкой, Docker запустит её через оболочку, и сигнал остановки до бота не дойдёт.

## Остановка

Когда сервис останавливают или перезапускают, systemd и Docker посылают процессу сигнал SIGTERM. `run_polling` его обрабатывает так же, как Ctrl+C:

1. перестаёт забирать новые события;
2. даёт хендлерам, которые уже работают, до 10 секунд, чтобы закончить;
3. отменяет те, что не успели;
4. закрывает соединения с мессенджерами и хранилище.

Время ожидания задаётся параметром: `dp.run_polling(*bots, shutdown_timeout=30)`. Оно должно быть меньше времени, которое даёт на остановку сам systemd (90 секунд по умолчанию) или Docker (10 секунд, меняется параметром `--stop-timeout`). Иначе процесс убьют раньше, чем он закончит. У Docker запас по умолчанию впритык к 10 секундам matele, поэтому в примере выше стоит `--stop-timeout 20`.

События, которые бот не успел забрать, не теряются: мессенджер какое-то время хранит их и отдаст после запуска.

## Чтобы события не терялись

По умолчанию matele подтверждает получение событий раньше, чем закончат работу их хендлеры. При обычной остановке это не проблема, хендлеры успевают доработать. Но если процесс убить посреди работы хендлера (кончилась память, выключился сервер), событие, которое он обрабатывал, пропадёт.

Для бота, который отвечает на вопросы, это не страшно: человек напишет ещё раз. Для бота, который принимает заказы или платежи, потерянное событие это потерянный заказ. Для таких есть режим «минимум один раз»:

```python
dp.run_polling(*bots, at_least_once=True)
```

В этом режиме событие подтверждается только после того, как хендлер закончил. Если процесс погиб, мессенджер пришлёт событие снова после перезапуска.

У режима есть цена, и о ней нужно знать заранее.

Событие может прийти дважды. Если процесс погиб, когда хендлер уже сделал своё дело, но получение ещё не подтверждено, после перезапуска хендлер будет вызван для того же события ещё раз. Поэтому хендлеры должны быть готовы к повтору: перед тем как создать заказ, проверить, не создан ли он уже.

Бот работает медленнее. Следующая пачка событий мессенджера запрашивается, только когда обработана вся текущая, так что один медленный хендлер задерживает остальных.

У вебхуков такой же режим включается параметром `Webhook(dp, at_least_once=True)`.

## Нагрузка

Одновременно обрабатывается не больше 100 событий одного мессенджера. Если событий приходит больше, чем хендлеры успевают обработать, остальные ждут своей очереди на стороне мессенджера, а не копятся в памяти бота. Число меняется параметром:

```python
dp.run_polling(*bots, concurrency=300)
```

Увеличивать его имеет смысл, если хендлеры в основном ждут: базу, внешний сервис, мессенджер. Если ваша база принимает не больше 20 соединений, ставить 300 бессмысленно.

Самое важное правило для async-бота: не блокируйте цикл событий. Пока хендлер выполняет долгий синхронный вызов (`time.sleep`, `requests.get`, тяжёлое вычисление), бот не обрабатывает никого. Используйте async-библиотеки, а то, что бывает только синхронным, выносите в поток:

```python
import asyncio


@dp.command("report")
async def report(ctx: Context):
    async with ctx.typing():
        pdf = await asyncio.to_thread(build_pdf, ctx.user.id)    # синхронная функция в отдельном потоке
    await ctx.reply_file(pdf, filename="report.pdf")
```

## Логи и ошибки

Настройте логирование в начале программы, иначе вы не увидите ни ошибок, ни предупреждений:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s: %(message)s")
```

И зарегистрируйте обработчик ошибок, чтобы человек получал ответ, когда хендлер упал:

```python
@dp.on_error
async def on_error(ctx: Context, exc: Exception):
    logging.exception("Ошибка в хендлере", exc_info=exc)
    await ctx.reply("Что-то пошло не так, мы уже разбираемся")
```

В этот же обработчик подключают сервисы сбора ошибок вроде Sentry. Что и на каком уровне пишет сам matele, описано в разделе [Логи](errors.md#логи).

В логах matele нет текстов сообщений: только тип события, мессенджер, id человека и чата. Если вы пишете в лог сами, помните, что там могут оказаться личные данные.

## Несколько процессов

Одному процессу хватает очень надолго: бот в основном ждёт сеть, а не считает. Если всё же нужно несколько процессов или серверов, вот что должно быть общим.

События. Только вебхуки: балансировщик раздаёт запросы мессенджеров между процессами. Polling с одним токеном в нескольких процессах не работает.

Секрет вебхука. По умолчанию он случайный и свой у каждого процесса. Задайте общий: `Webhook(dp, secret=os.environ["WEBHOOK_SECRET"])`.

Состояния. `RedisStorage` вместо SQLite. Он же следит, чтобы два процесса не обрабатывали события одного человека одновременно.

Ключи длинных кнопок Telegram. Они хранятся в памяти процесса или в файле SQLite, и другой процесс о них не знает. Либо держите данные кнопок короче 64 байт, либо напишите общее хранилище по протоколу `AliasStore` (см. [Длина данных](buttons.md#длина-данных)).

Скорость рассылок. Ограничение скорости в `Hub` действует внутри процесса. Если рассылают несколько процессов, разделите лимит между ними.

Секрет подписи кнопок, если вы ей пользуетесь, тоже должен быть один на всех.

## Перед выпуском

Короткий список того, что стоит проверить:

- токены лежат в переменных окружения, а не в коде;
- подключено постоянное хранилище состояний;
- сервис перезапускается сам после падения и после перезагрузки сервера;
- есть обработчик ошибок, и логи куда-то пишутся;
- есть хендлер для устаревших кнопок (`@dp.raw_callback()`);
- весь текст снаружи проходит через `escape()`;
- в хендлерах кнопок проверяются права, а не только данные кнопки;
- бот проверен руками в обоих мессенджерах, в личном чате и в группе.
